# iceland-trip.html：每日地圖、安全資訊、Day 導覽列、住宿總整理

日期：2026-08-05
對象檔案：`iceland-trip.html`（暫不同步回 `family-trip-template.html`，見「與模板的關係」）

## 背景

使用者參考另一款旅遊 app 的四項功能，要加進冰島版：

1. 上排 Day 總覽按鈕列（總覽 / D1 / D2 …）
2. 每日行程最下方的安全資訊（附近警局、急診）
3. 每日行程最上方的地圖（依當天景點自動繪製）
4. 總覽頁的住宿總整理

行程為 2026-09-14 起 20 天的冰島挪威自駕，成員四人。

## 核心約束：離線可用

使用者明確要求安全資訊「現場出事時要能用，含沒訊號」。冰島 Ring Road 有大段無行動訊號，而安全資訊的使用時機正是緊急時刻。

**現況**：這支 app 目前離線完全打不開。Firebase Realtime Database 的 **web** SDK 沒有磁碟持久化（`setPersistenceEnabled` 只存在於 iOS/Android SDK，Firestore 的 `enableIndexedDbPersistence` 不適用 RTDB），而 `saveDevice()` 只存 `{url, apiKey}`，沒有任何資料快取。

因此本次必須先鋪一層 localStorage 快照，否則功能 2 的離線需求無法達成。這是四項功能之外的地基工作。

## 實測結果（設計依據）

所有外部相依都以使用者的真實行程資料實測過，不是憑記憶假設。

### 行程現況

20 天中 14 天完全空白，總計 14 個活動、12 筆有 `loc`、住宿僅 3 筆。行程仍在早期規劃階段，所有功能都必須在「資料很少」的狀態下表現正常。

### Nominatim 地理編碼

以 12 筆真實 `loc` 測試：

- 直接查原字串：5 筆成功、7 筆失敗
- 加上查詢字串正規化後：9 筆成功、3 筆失敗
- 查不到的全是**小型公寓民宿**（OSM 未收錄）與一筆連鎖賣場

正規化救回的四種模式：

| 失敗原因 | 例 | 有效的候選字串 |
|---|---|---|
| 尾端距離標記 | `<地名> 9.6km` | 去掉距離後綴 |
| 破折號接副標 | `<飯店> - <集團名>` | 取破折號前段 |
| 尾端雜訊詞 | `<峽谷> Masjid` | 去掉通用/雜訊詞 |
| 描述性語句 | `Glacier Walk on <冰川> Glacier` | 取最長的非通用詞 token |

### 兩種「編造答案」的陷阱

外部服務查不到時不會誠實回報，而會給出看似正常、實際錯誤的結果：

1. **Photon 語意不符**：查詢某公寓民宿，回傳名稱完全不同的另一家公寓；查詢另一筆，回傳同名但位於相隔約 300 公里的行政區。
2. **`countrycodes` 限定反而製造錯誤**：`Bergen`（挪威第二大城）限定 `countrycodes=is` 時，回傳冰島東部某條街上的建築物，與真實位置相距約 1400 公里。

這與 travel-atlas 踩過的坑同類（不限國家時「錦市場」被判成北京的批發市場），但方向相反 —— 該案例是限定國家才修好，本案例是限定國家才出錯。結論不是「該不該限定國家」，而是**任何來源的結果都必須通過獨立的合理性檢查**。

### 國家範圍

行程含挪威段。實測 `countrycodes=is,no`：挪威地點正確，且冰島地點的結果與限定 `is` 時完全相同。故一律使用 `is,no`。

### Overpass（警局／急診）

- 冰島鄉下資料稀疏：某東南部城鎮半徑 50 km 內僅 2 筆
- **警局可能完全沒有 `name` 標籤**（實測某南岸小鎮只有 `amenity=police`）
- 鄉下常只有 `clinic`（heilsugæsla）而無 `hospital`，故三類都要查
- 公共 server 會限流，實測期間被擋過一次

### OSRM（車程）

冰島路網查詢全數成功。直線距離與實際車程的落差：

| 路線類型 | 直線 | 車程 | 時間 | 倍率 |
|---|---|---|---|---|
| 冰川湖 → 東南城鎮診所 | 62.4 km | 75.2 km | 65 分 | 1.20x |
| 西南溫泉 → 首都急診 | 38.1 km | 47.3 km | 47 分 | 1.24x |
| 南岸瀑布 → 小鎮警局 | 53.3 km | 61.5 km | 55 分 | 1.15x |

以上皆為 Ring Road 直路；繞峽灣路段落差會更大。關鍵不在誤差比例，而在「直線 62 公里」無法傳達那是一小時車程。**採用車程，直線僅作 fallback。**

## 資料模型

### Firebase 新增路徑

```
/schedule/{did}/acts/{aid}/geo = {lat, lng, q, src, at}
    q   實際查詢成功的字串（正規化後，非原始 loc）
    src 'nominatim' | 'photon' | 'manual'
    at  ISO timestamp

/schedule/{did}/acts/{aid}/geoFail = {at, tried:[...], reason}
    reason 'no-match' | 'sanity-reject' | 'network'

/safety/{did} = {
    base:     {lat, lng, from:'hotel'|'center'|'prevHotel', label},
    police:   [{name, lat, lng, km, drive:{km,min}}],    // 最近 3 筆
    hospital: [{name, lat, lng, km, emergency, drive:{km,min}}],
    at
}
```

座標掛在活動底下，因為它是活動的屬性：活動刪除時一併消失不留孤兒，`moveAct()` 跨日搬移時座標自動跟著走，不需要額外同步邏輯。這刻意避開既有的痛點 —— 記帳與行程僅靠日期字串綁定，所以每次變動日期都必須記得同步 `/expenses/*/date`。

安全資訊另置 `/safety/{did}`，因為它是可整包丟棄重算的衍生資料，不應混進行程本體。

`_fbListen()` 監聽根路徑 `/`，故新路徑會自動隨既有 listener 回傳，不需要第二個 listener。

### localStorage 快照

key：`iceland_trip_snap`

`_fbListen()` 取得 `snap.val()` 時寫入一份完整快照；開 app 時先以快照渲染，Firebase 連上後覆蓋。

**必須排除 `acts.*.images`**：照片以 base64 直接存在活動中，單張 100–500 KB、每個活動上限 6 張，而 localStorage 單一網域上限 5 MB。不排除會導致寫入失敗，連行程文字都存不進去。

代價：離線時不顯示照片。行程、地點、住宿、安全資訊、記帳均不受影響。

估算：目前資料 2.5 KB；20 天填滿並含座標與安全資訊約 60–100 KB。

## 座標解析管線

### `geoCandidates(raw) → string[]`

產生候選查詢字串，依序嘗試至第一個通過檢查者為止。採「多候選實查」而非「單一正規化規則」，因為每個候選都經真實查詢驗證，而非猜測。

順序：

1. 原字串
2. 去尾端距離標記（`\s+\d+(\.\d+)?\s*(km|公里|m)$`）
3. 破折號／連字號前段
4. 去除通用詞後的剩餘（Glacier、Walk、Tour、Restaurant、Hotel、Apartment、Wholesale、Masjid 等）
5. 最長的非通用詞 token

查到即停，故正常地點只打一次 API。

### `sanityCheck(hit, did) → bool`

1. **國家**：`is` / `no` 以外一律拒絕。Nominatim 由 `countrycodes=is,no` 保證；Photon 無此參數，須檢查回傳的 country 欄位。
2. **距離**：與當天其他已知座標的中心超過 **200 km** 即拒絕。這是唯一能擋下前述兩種「編造答案」的機制。

**解析順序的陷阱**：距離檢查依賴「當天其他已知座標」，故第一筆解析時無參照可用。若此時採信了一個錯誤座標，它會成為後續檢查的基準，反而把正確的座標擋掉。

因此兩種來源的無參照行為不同：

- **Nominatim 無參照時可採用**。它由 `countrycodes=is,no` 限定範圍，錯誤模式已知且有限。
- **Photon 無參照時一律拒絕**，記為 `sanity-reject`。它是不可靠來源（實測會回傳語意不符的結果），沒有第二個座標可交叉驗證就不該採信。

如此可確保錯誤座標不會成為基準。

### `geoResolve(raw, did) → {lat,lng,src,q} | null`

候選逐一試 Nominatim → 通過 `sanityCheck` 即採用 → 全數失敗才試 Photon（套用同一套 `sanityCheck`）→ 仍失敗回 `null` 並寫入 `geoFail`。

### `geoQueue`

1.1 秒節流的序列佇列。Nominatim 使用政策要求每秒至多 1 次請求，不可省略。

### `ensureActGeo(sched)`

掃出「有 `loc`、無 `geo`、無 `geoFail`」的活動排入佇列。`reason:'network'` 的 `geoFail` 視為可重試。

### 多裝置競態

四台裝置可能同時解析同一筆。結果冪等（寫入相同座標），且第一台寫入後其餘裝置的 listener 會收到 `geo` 而跳過。代價僅為少量重複請求，**不加鎖** —— 複雜度換不到等值的好處。

## 安全資訊管線

### `dayBaseLatLng(did) → {lat,lng,from,label} | null`

依序：當日住宿座標（`cat==='hotel'` 且有 `geo`）→ 當日所有有座標活動的地理中心 → 前一日住宿座標。皆無則回 `null`，該日不顯示安全資訊區塊。

### `fetchSafety(base)`

Overpass 查詢 `amenity=police` / `hospital` / `clinic`，node 與 way 皆查（醫院常繪為 way）。

半徑漸進：10 km → 30 km → 100 km，取到結果即停。

各類取最近 3 筆。對每筆呼叫 OSRM 取得 `drive:{km,min}`，同時保留 Haversine 直線距離作 fallback。

節流：Overpass 間隔 ≥ 2 秒，失敗重試一次。OSRM 間隔 1 秒。

### `ensureSafety(sched)`

掃出缺 `/safety/{did}` 的日期，或 `base` 已變動者，排入佇列。

**`base` 變動的判定**：重新計算當日 `dayBaseLatLng()`，與已存的 `safety.base` 相距超過 **1 km** 才視為變動並重抓。設此門檻是因為 `from:'center'` 的中心點會隨當天新增／刪除活動而微幅漂移，若逐次重抓會在每次編輯行程時浪費 Overpass 與 OSRM 請求，而數百公尺的位移不會改變「最近的警局是哪一間」。

## 使用者介面

### 功能 1：Day 導覽列 `renderDayStrip(sched)`

Sticky 於 `#schedBox` 上方，橫向捲動的 chip 列：`總覽 / D1 9/14 / D2 9/15 …`。

- 點擊日期 chip → `scrollIntoView({behavior:'smooth'})` 至該日卡並展開
- `IntersectionObserver` 做 scrollspy：捲到哪天即 highlight 對應 chip，並將其帶進可視範圍
- 「總覽」chip 捲回頁面頂端的總覽區塊，非切換頁面狀態

字級比照本 app 慣例（使用者含長輩，老花友善）：日期 18px、Dn 標籤 15px。

### 功能 4：總覽區塊 `renderOverview(sched)`

固定於所有日卡之上。掃出所有 `cat==='hotel'` 的活動依日期排序，列出日期 / 名稱 / 地點，有座標者附導航按鈕。無住宿的天數不列出。

連續數晚同一住宿的合併顯示（如 `9/16-9/18`）**本次不做**，待行程填完再評估。

### 功能 3：每日地圖

掛於日卡展開後的最上方，**跟隨日卡展開狀態 mount / unmount**。如此不需地圖自身再做一層收合，也避免 20 天全展開時同時建立 20 個 Leaflet 實例。

- 當天有座標的活動繪為編號 marker（依 `order`）+ 虛線連接
- 僅 1 點：zoom 13 定位該點
- **0 點：整塊不顯示**，不留空框
- Leaflet 自 CDN 延遲載入（第一次需要時才載）

**重繪衝突與解法**：`renderSched()` 每次 `box.innerHTML = …` 整頁重畫，而 listener 監聽根路徑 —— 記一筆帳即觸發重畫，會使 Leaflet 實例變殭屍並閃爍（同 travel-atlas 地球儀 `globeBoundCanvas` 那類坑）。

解法：`renderSched()` 開頭先將現有 `.day-map` 元素自 DOM 取下存入 `Map(did → el)`，`innerHTML` 重畫後再 `appendChild` 回對應日卡並呼叫 `invalidateSize()`。Leaflet 實例在 detach 期間仍有效。

### 功能 2：安全資訊卡

掛於日卡展開後的最下方。

- 最近警局、最近急診醫院，各含名稱、車程（`75.2 公里 · 約 65 分`）、導航按鈕
- **名稱可能不存在**，須顯示「警察局（未命名）」而非空白
- 有急診者加註標記（`emergency=yes`）
- 底部明寫依據：「依住宿 ⟨名稱⟩ 查詢」／「依當日行程位置查詢」
- 底部加註「資料：OpenStreetMap · 車程僅供參考，出發前請再確認路況」（冰島秋冬路況與 Ring Road 封閉會使時間嚴重失真）

### 設定頁：離線資料狀態面板

```
離線資料狀態
  地點定位   9 / 12 已完成
  安全資訊   4 / 20 天已就緒
  查不到座標：⟨清單⟩
  [ 立即更新 ]
```

以現有資料，安全資訊可就緒的是有活動座標的那 4 天；其餘 16 天因無任何座標而無法定位，屬資料尚未填寫的正常結果，不算失敗。

查不到的清單直接指出該修正哪幾筆 `loc`。`sanity-reject` 者另行標示，因其可能為誤判，使用者有權知道並手動覆寫。

## 錯誤處理

原則：**任何外部相依失效都不得使行程頁無法開啟**。

| 相依 | 失敗行為 | 使用者看到 |
|---|---|---|
| Nominatim / Photon | 記 `geoFail`，不自動重試 | 該活動無 marker，狀態面板列出 |
| Overpass 限流 | 保留舊快取不覆蓋，隔 2 秒重試一次 | 上次資料 + 更新時間 |
| OSRM | 退回直線距離 | 標示「直線 62 公里」 |
| Leaflet CDN | 走離線降級路徑 | 地點清單 + 導航連結 |
| Firebase 斷線 | 使用 localStorage 快照 | 頂部「離線 · 顯示 ⟨時間⟩ 的資料」 |

**不得吞掉錯誤。** 財務 app 曾因前端 `catch` 吃掉錯誤，導致 401、500、空資料表現完全相同，最終須自行帶 `x-api-key` 打 API 才能分辨。此處三種失敗必須可區分：

- `no-match`：OSM 確實無此地點 → 不自動重試（避免無限打 API），使用者修改 `loc` 或按「立即更新」才重查
- `sanity-reject`：查到但被距離檢查擋下 → 面板特別標示
- `network`：服務當下不通 → 下次開 app 自動重試

現有 `sync()` 擴充為三態：已同步 / 同步中 / 離線（附快照時間）。

## 驗收標準

單檔無 build 的 PWA，專案慣例為手動驗證。不引入測試框架 —— 會破壞 single-file 架構且換不到等值好處。

### 以真實資料驗收

執行「立即更新」後，既有 12 筆 `loc` 應為 9 筆取得座標、3 筆列入查不到清單（兩筆公寓型住宿、一筆連鎖賣場）。

公開地標的預期結果（可直接核對）：

| 查詢 | 預期座標 |
|---|---|
| Seljalandsfoss | 63.6155, -19.9882 |
| Skógafoss | 63.5321, -19.5113 |
| Blue Lagoon（去距離後綴後） | 63.8792, -22.4443 |

### 必測迴歸點

1. 記一筆帳後，展開中的地圖不得閃爍或成為殭屍實例
2. 跨日拖曳活動仍正常，且座標隨之搬移
3. DevTools 切 offline 重開 app，行程與安全資訊皆須存在
4. 兩台裝置同時開啟時，既有的行程日期補正機制不得被破壞（不可互踢）
5. iOS 拖曳的四項既有修法不得被改動（`touch-action:none`、不等 Firebase 回應即啟動、就近判定、`touchcancel` 處理）

## 實作順序

各階段皆可獨立驗證後再進下一階段：

1. **localStorage 快照 + `sync()` 三態** —— 地基，其餘功能的離線行為都依賴它
2. **座標解析管線 + 設定頁狀態面板** —— 功能 2、3 的前提；面板先做才能看見解析進度與失敗原因
3. **功能 1 Day 導覽列** —— 無外部相依，獨立可驗
4. **功能 4 總覽住宿** —— 依賴階段 3 建立的總覽區塊，不依賴座標
5. **功能 3 每日地圖** —— 依賴階段 2 的座標
6. **功能 2 安全資訊** —— 依賴階段 2 的座標與階段 1 的快照

## 不做的事

- 預先下載地圖圖磚至裝置（OSM 圖磚服務政策禁止批量下載；離線改以地點清單降級）
- 連住多晚的住宿合併顯示（待行程填完再評估）
- 將本次功能同步回 `family-trip-template.html`（見下）
- 中文地名的地理編碼（冰島 OSM 無中文標籤，實測繁中查詢全數失敗；`loc` 須以英文或冰島文填寫）

## 與模板的關係

`iceland-trip.html` 與 `family-trip-template.html` 為同源分身，共同功能原則上兩邊都要改，但冰島版已刻意移除 Gemini 收據掃描整條路徑。

本次四項功能**先只做冰島版**。其中安全資訊與地圖高度依賴 `countrycodes=is,no` 與冰島路網特性，泛化回模板需要另行設計國家範圍的取得方式，不在本次範圍。

## 已知的既有風險（不在本次範圍，但應排程）

Firebase 安全性規則的收斂應於 2026-09-14 出發前完成。步驟順序不可跳過：先部署 → 啟用匿名登入 → 四人各自於裝置貼上金鑰 → 確認皆可讀取 → 才發布規則。順序錯誤會把自己鎖在門外。細節見既有的 Firebase 匿名登入與安全性規則筆記。
