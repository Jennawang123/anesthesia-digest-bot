# 行程活動多筆花費設計

日期：2026-08-30
範圍：`iceland-trip.html`、`family-trip-template.html`、`couple-trip-template.html`、`us-trip.html`（四支都有這套「活動花費自動同步記帳」子系統，逐字相同，跟上次只有三支有的跨夜住宿子系統不同）

## 問題

編輯活動時金額只有一格（`a_cost`），存成 `act.cost={amt,cur,paidBy}` 單一物件，儲存時用固定 id `actcost_{did}_{aid}` 同步成一筆 `/expenses` 記帳紀錄——所以一個活動最多只能連到一筆花費。實際上一站常常有好幾筆各自的花費（門票、午餐、紀念品），現在只能挑一筆填或另外去記帳分頁分開新增（但分開新增就跟這個活動脫鉤，行程卡片上看不到）。

## 決策

| 項目 | 決定 | 理由 |
|---|---|---|
| 資料模型 | `act.cost`（物件）→ `act.costs`（陣列） | 使用者確認要在行程編輯視窗裡直接多行填寫，不是另開視窗連結既有記帳項目。 |
| 幣別／付款人 | 每行各自選，不是整個活動共用一組 | 使用者 2026-08-30 拍板：偶爾會有不同人付、不同幣別的情況（如一人付門票、一人請客午餐）。 |
| 幣別／付款人的表單元件 | 原生 `<select>` 下拉，不沿用現有整排 chip 按鈕 | chip picker 一份就要佔一整條寬度，乘上可能 3-4 行會把表單拉得很長；下拉選單省空間。 |
| 描述欄位 | 每行加一個短描述輸入框 | 使用者拍板：沒有描述的話，這幾筆花費在「記帳」分頁會全部顯示成同一個活動名稱，分不出哪筆是哪筆。 |
| 舊資料相容 | 不寫遷移腳本，讀取端 fallback | 既有活動的 `act.cost`（單一物件）用 `act.costs || (act.cost?[act.cost]:[])` 這種寫法在讀取時當成一筆陣列處理；使用者下次編輯儲存那筆活動時才會自然轉成新格式。四支各自有獨立 Firebase，沒有共用資料庫可以一次遷移，寫遷移腳本要對四個 DB 各跑一次，不划算。 |

## 設計

### 資料結構

```js
act.costs = [
  {desc:'門票', amt:1200, cur:'JPY', paidBy:'Mike'},
  {desc:'午餐', amt:350,  cur:'JPY', paidBy:'Monica'},
]
```

`desc` 可空字串（記帳分頁該筆就顯示活動名稱，不顯示描述）。不再使用 `act.cost`（單數），但讀取端永久保留 fallback，不主動清除舊欄位（沒被使用者碰過的活動不用管）。

新增一個小工具函式 `actCostList(act)`，回傳統一格式的陣列（新格式直接回傳、舊格式包一層陣列、都沒有回傳空陣列）。行程卡片顯示、`moveAct()`、`delAct()` 都呼叫這個函式取得「這個活動有哪幾筆花費」，不要各自重寫一次 fallback 邏輯。

### 表單 UI

`.cost-box` 區塊從單一「金額＋幣別＋付款人」改成可重複的清單：每行「描述（短文字）＋金額＋幣別下拉＋付款人下拉＋✕ 刪除」，下方一個「＋ 加一行」按鈕。新增一行時，幣別／付款人預設帶入上一行的選擇（同一站的花費通常同幣別、常常同一人先墊），減少每行都要重選的操作。

沿用 `curActImages`（現有「活動圖片」清單）那套「JS 陣列驅動 + 每次變動整段重繪 innerHTML」的既有模式，新增對應的 `curActCosts` 陣列與 `renderActCostRows()` 函式，不另創一套機制。

### 同步到記帳

- 現在：儲存活動時，固定 id `actcost_{did}_{aid}` 整筆覆蓋一份 `/expenses` 記錄。
- 改成：`actcost_{did}_{aid}_{n}`（`n` = 陣列索引），逐行各自 `set` 一份記帳記錄。儲存時如果新陣列比舊資料短（使用者刪掉了某幾行），要把索引 `n>=新長度` 的舊記錄一併刪除，不然會留下孤兒記帳項目——這裡需要讀出「儲存前這個活動有幾行」才知道要刪到哪個索引，跟現有 `saveAct()` 已經在讀的 `prev`（`dayData.acts[id]`）用同一次讀取，不必多一次 Firebase 來回。
- `delAct(did,aid)`：現在是直接砍一個固定 id；改成要先讀出該活動的 `costs` 長度，再逐一砍 `actcost_{did}_{aid}_0` 到 `_{n-1}`。
- `moveAct(fromDid,aid,act,toDid)`：現在是搬一筆；改成逐行搬（複製到新 did 底下的對應索引、砍掉舊 did 底下的），沿用同一個 `newDate`。

### 不受影響的部分

- `fixDates()` 裡辨認記帳歸屬日的正規表達式 `/^actcost_(day\d+)_/` 只看前綴，加上 `_{n}` 尾碼不影響比對，不用改。
- `calcDaySpend`／`calcMemberSpend`／圓餅圖統計：這些都是掃過 `/expenses` 整個平面清單加總，不管一個活動底下有幾筆記帳項目，本來就會全部算進去，不用改。
- 「記帳」分頁本身的新增/編輯/刪除（`openExpM`／`saveExp`／`delExp`）完全不動——那是給不掛活動的一般支出用的，跟這次改動是兩條平行路徑，行為不變。

### 行程卡片顯示

現在：`act.cost?.amt>0` 才顯示一行「💰 ¥1,200」。

改成：對 `actCostList(act)` 的每一筆各畫一行，有描述就帶上（「💰 門票 ¥1,200」），沒描述就跟現在一樣只顯示金額。多筆就疊著顯示，不做摺疊——預期一個活動頂多 2-4 筆，摺疊反而多一次點擊。

## 測試

`_selftest()` 新增：
- `actCostList()` 對新格式（`costs` 陣列）、舊格式（單一 `cost` 物件）、兩者都沒有這三種輸入的回傳值
- 手動用 Playwright 灌假資料驗證：新增活動填兩行花費存檔後，`/expenses` 底下出現兩筆 `actcost_*_0`／`actcost_*_1`；把其中一行刪掉重新存檔後，`actcost_*_1` 那筆從資料裡消失（不是留著金額歸零的孤兒記錄）
- 行程卡片渲染：兩筆花費各自顯示一行、金額與描述正確

四支各自跑一次。

## 部署
